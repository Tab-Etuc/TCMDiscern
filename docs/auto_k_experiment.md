# 自動候選數量實驗：TCM-SD BM25 + 二分搜尋

日期：2026-11-11

## 方法與資料界線

- **Train 43,180** 筆，索引只含主訴、病情敘述、四診文字。訓練病例的 `norm_syndrome` 僅用於將病例的 BM25 分數聚合為證型分數。
- **Dev 5,486** 筆，只用來計算 Recall 與搜尋 K。沒有讀取 Test。
- 稀疏方法：**CJK Bigram BM25**，標準 `k1=1.5, b=0.75`；對每個訓練證型取該類中匹配度最高的病例分數，得到 148 個互異候選證型排名。
- 所有候選排名只計算一次，二分搜尋在已保存的排名上查詢 Recall@K。
- 另外建立去除與 Train **完全相同四診文字**及 Train 既有 `user_id` 的 Dev 子集，共 **4,953** 筆；這只是一種部分去洩漏檢查，**不包含語意近重複排除**。
- 本實驗**沒有訓練或評估 Gemma LoRA**；其真正的端到端 Top-1 尚未知。

### 二分搜尋結果

| 門檻 | 最小 K（原始） | 最小 K（部分去重） |
|---|---:|---:|
| Micro Recall ≥95% | 5 | 5 |
| Micro Recall ≥98% | 12 | 12 |
| Macro Recall ≥90% | 17 | 17 |
| Macro Recall ≥95% | 34 | 35 |
| Macro Recall ≥98% | K≤50 無解 | K≤50 無解 |

若同時要求 **Micro ≥95%、Macro ≥90%**，應選 **K=17**。若同時要求 **Micro ≥95%、Macro ≥95%**，則需 **K=35** 才在部分去重驗證集也達標。

實際的 Micro 95% 搜尋路徑（K=1～50）：

```text
K=25 → 99.07%：往更小搜尋
K=12 → 98.16%：往更小搜尋
K= 6 → 96.32%：往更小搜尋
K= 3 → 92.75%：往更大搜尋
K= 4 → 94.57%：往更大搜尋
K= 5 → 95.46%：找到最小 K
```

## 如何重現

```bash
uv sync --python 3.12 --dev
uv run python scripts/auto_k_bm25.py --max-k 50 --targets 0.80 0.85 0.90 0.95 0.98
```

本機產出：

- `data/reports/bm25_binary_k_dev.json`：1～50 全曲線、Micro/Macro 搜尋步驟、原始／部分去重比較
- `data/candidates/bm25_dev.jsonl`：Dev 的 148 證型中前 50 名候選及 Dev 金標（僅用於研究評估／未來 LoRA 验證，不得作訓練）
- `data/reports/bm25_binary_k_dev_smoke.json`：前 100 筆的程式驗證結果

全部位於 Git 忽略的 `data/`，不會上傳原始病例或 Dev gold。

## 下一階段：Gemma 的 K 搜尋方式

對 **Recall@K** 可用二分搜尋，因為候選池增加只會提高或維持涵蓋率。對 **Gemma Top-1** 不可直接二分搜尋最大值：K 增加時準確率不保證單峰，也可能因候選互相干擾而下降。

應用相同 LoRA checkpoint 與相同 Dev，先用少量探索性 K 找到高分區間，再在附近細搜；所有評估需要記錄已測 K、分數、耗時及候選順序敏感性。最後以 Dev Top-1 與 Macro-F1、平均 K、推論成本選擇方案，再在 **Test 一次性評估**。實作前不可把 BM25 Recall 當作 Gemma 的最終準確率。

注意：目前尚未完成 Hybrid、Embedding 與 Gemma 實驗；本文件僅報告真正執行的 BM25 基準及 K 搜尋結果。
